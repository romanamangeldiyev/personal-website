01 — Problem

Education has many stakeholders, but most conversations happen in silos.

Students experience the system differently from teachers. Parents optimize for different outcomes than researchers. Institutions operate with constraints that are often invisible to everyone else. I wanted to explore a product where those perspectives are not separate communities but inputs into the same structured discussion.

The opportunity was not “build another social network.” It was “design a better container for a difficult multi-stakeholder conversation.”

02 — Product hypothesis

An agora may be more useful than a feed.

The core hypothesis is that discussion quality improves when the product makes context and participant perspective explicit. Instead of one infinite feed, PlatoMind organizes conversation around topics and agora-like spaces where roles can challenge and build on one another’s arguments.

Target participants

Students, professors, teachers, parents, researchers, psychiatrists, philosophers, and other people with a meaningful perspective on education. The product is deliberately multi-sided because the value comes from interaction across those roles.

03 — PM decisions

Prototype the interaction model before the platform.

I deliberately did not begin with accounts, databases, notifications, recommendation systems, or moderation infrastructure. Those are expensive layers to build before knowing whether the core conversation model is actually useful.

  • Agora over feed: organize around a problem or topic rather than passive content consumption.
  • Roles as product context: make the participant’s perspective part of how the discussion is understood.
  • Mock data first: test information architecture and screen behavior without backend dependency.
  • Graceful AI fallback: the Ask composer can assist with routing, but manual selection remains possible.
  • Delay infrastructure: only add persistence and moderation after the interaction model earns it.

What I would measure

I would look beyond generic engagement. Useful signals would include cross-role reply rate, percentage of questions routed to a relevant agora, discussion depth, return rate after receiving a substantive response, and whether users report that another perspective changed or sharpened their view.

04 — Experience model

Designing the conversation itself.

The interface centers on topic-driven spaces, role-aware participants, and an Ask flow that moves a question toward the right discussion context. The prototype is meant to answer product questions before engineering questions.

user has a question → expresses it in plain language → route to a relevant agora → surface multiple stakeholder perspectives → continue structured discussion → learn whether the format creates better insight
05 — Prototype strategy

The architecture is intentionally cheap to change.

PlatoMind uses a static HTML shell, React and Babel in the browser, a JavaScript application file, custom CSS, and local mock data. There is no production backend in this version.

From an engineering perspective, this is deliberately unsophisticated. From a product perspective, that is the point: the cost of changing the concept stays low while the highest-risk assumption — whether the discussion model is compelling — is still unvalidated.

06 — Publishing

Make the prototype easy to put in front of people.

Because there is no build step or server dependency, the prototype can be published as static files through GitHub Pages or another static host. That makes iteration and sharing fast.

  • Keep the prototype files at the repository root.
  • Publish directly from the deployment branch.
  • Load React, Babel, and fonts from CDNs.
  • Preserve manual interaction paths when optional AI assistance is unavailable.
07 — Validation & next

The next build depends on what users do, not what the roadmap says.

If the interaction model proves useful, the next product layer would be persistent identity, saved discussions, moderation, search, and role-aware discovery. If users do not find the cross-perspective format meaningfully better, adding infrastructure would only make the wrong idea more expensive.

This project is useful to me as both a PM and an engineer because it forces a sequencing decision: identify the riskiest product assumption first, then choose the cheapest technical implementation that can test it.
