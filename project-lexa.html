01 — Why I built it

Why I built it

Legal systems are difficult to navigate when the user does not know the correct legal terminology, which institution is responsible, or what a formal application should look like. Lexa starts from the opposite direction: the person explains the problem in ordinary language and the system translates that into a structured legal process.

The product question was simple: can legal software begin with the user’s problem instead of forcing the user to understand the legal system first?

I designed Lexa around three roles — citizen, lawyer, and ministry — so the same underlying case can be understood differently depending on who is working with it.

02 — What it does

From a problem statement to a legal workflow

The citizen describes what happened. The system classifies the issue, asks follow-up questions when important facts are missing, searches the relevant legal knowledge, and builds a structured draft that can be reviewed before it is used.

  • Natural-language intake instead of form-first interaction.
  • Issue classification and missing-information collection.
  • Semantic retrieval over legal material.
  • Structured generation of formal documents.
  • Separate product surfaces for citizens, lawyers, and ministry workflows.
03 — Architecture

Architecture and technology choices

The codebase is split into a web application, an API, shared contracts, infrastructure, and documentation. That separation lets the UI evolve independently while keeping the legal workflow and retrieval logic inside the backend.

The local development environment is containerized for infrastructure services. The API uses migrations rather than ad-hoc schema changes, while Qdrant handles vector retrieval and Redis supports fast state-oriented workloads.

04 — Build process

How I’m building it

I’m building Lexa in phases instead of trying to make the entire legal platform intelligent at once. The first phase established the repository structure, infrastructure, web/API boundaries, data layer, and development workflow.

user problem → intake + classification → missing-fact questions → retrieval → legal reasoning workflow → document draft → human review / next action

The main engineering constraint is traceability. A legal product should make it possible to understand where information came from and which step transformed it. That pushes the architecture toward explicit graph states and retrieval rather than one giant prompt.

05 — Release process

Development and release workflow

Locally, infrastructure runs through Docker Compose while the FastAPI and Next.js applications run independently for fast iteration. Database changes go through Alembic migrations, and backend checks include tests, Ruff, MyPy, and migration validation.

  • Start Postgres, Qdrant, Redis, and MinIO through Docker Compose.
  • Run migrations before starting the API.
  • Run backend tests and static checks before a release.
  • Run lint, typecheck, and production build for the Next.js frontend.
  • Keep model integrations optional so the core application can still be tested without live LLM calls.
06 — What I’m learning

What this project is teaching me

Lexa is less about adding a chatbot to legal documents and more about designing a reliable product around uncertain language, retrieval quality, state, and formal output. The difficult part is not generating text; it is creating a system whose intermediate decisions are inspectable enough to improve.

The next work is focused on deeper legal retrieval, better workflow evaluation, and turning the prototype architecture into a product that can support real case flows safely.
