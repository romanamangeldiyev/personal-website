01 — Problem

The problem starts before the law.

People often reach a legal system without knowing the legal category of their problem, the institution responsible for it, or the structure a formal application should follow. That means the first barrier is not legal reasoning alone — it is translating a messy real-life situation into the language and sequence the system expects.

My starting question: can the product reduce the distance between “this happened to me” and “this is the next useful legal action”?

I chose this problem because it combines product ambiguity with a hard technical constraint: the experience must feel simple to the user while the system behind it remains structured, traceable, and reviewable.

02 — Product framing

Who is the product for, and what job is it doing?

The primary user is a citizen who has a concrete legal problem but may not know how to describe it in legal terms. Lawyers and ministry-facing workflows are secondary roles because they need a more structured representation of the same case.

Core job to be done

Help a person turn an unstructured problem into a complete enough case record and a useful next-step document without asking them to understand the legal system first.

MVP hypothesis

The first useful version does not need to “solve law.” It needs to reliably collect the right facts, retrieve relevant material, explain what is missing, and produce a draft that a human can inspect and correct.

03 — PM decisions

Product decisions before model decisions.

I treat Lexa as a workflow product, not a chatbot. That changes what gets prioritized. The important outcome is not whether a response sounds intelligent; it is whether the user reaches a clearer, more complete and reviewable next step.

  • Conversation-first intake: start with the user’s own language instead of forcing a legal form at the beginning.
  • Progressive questions: ask only for missing information that materially changes the next step.
  • Human-review boundary: generated documents should be inspectable before they are treated as final output.
  • Traceability over magic: product trust depends on showing where retrieved legal material and intermediate decisions came from.
  • Scope discipline: build one reliable end-to-end workflow before expanding into many legal categories.

What I would measure

I would validate the MVP with case-completion rate, number of clarification turns, percentage of drafts requiring major correction, retrieval relevance, time-to-useful-draft, and where users abandon the flow. These are validation targets, not claimed production metrics.

04 — Product flow

From an unstructured problem to a reviewable output.

user explains the problem → classify the case → identify missing facts → ask targeted follow-up questions → retrieve relevant legal material → build structured case state → generate formal draft → human review / next action

This sequence is intentionally visible in the product model. Each step has a reason to exist and can be evaluated separately, which makes both product iteration and technical debugging more useful than treating the whole experience as one prompt-response loop.

05 — Engineering

Architecture follows the product workflow.

The codebase separates the web experience, API, shared contracts, infrastructure, retrieval, and orchestration. The goal is not architectural complexity for its own sake; it is to keep state, retrieval, and document generation explicit enough to test and improve independently.

Frontend
Next.js · TypeScript · Tailwind
API
FastAPI · SQLAlchemy · Alembic
Orchestration
LangGraph
Primary data
PostgreSQL
Retrieval
Qdrant
State / services
Redis · MinIO

LangGraph fits the product because the interaction is stateful and multi-step. Qdrant supports semantic retrieval, PostgreSQL keeps durable application state, and migrations keep the data model versioned as the product changes.

06 — Build & release

Ship in phases, not as one giant AI feature.

The development plan starts with infrastructure and one inspectable workflow, then expands only after the flow is testable. Locally, infrastructure services run through Docker Compose while the FastAPI and Next.js applications can iterate independently.

  • Version database changes with Alembic migrations.
  • Run backend tests, Ruff, MyPy, and migration checks before release.
  • Run frontend lint, typecheck, and production build.
  • Keep live model calls optional in tests so core product behavior can be validated deterministically.
  • Release workflow improvements separately from model changes so failures can be isolated.
07 — Validation & next

The next milestone is product evidence, not more features.

The most important next step is testing whether users can complete a realistic legal flow with less confusion and whether the resulting draft is useful enough for review. That means evaluating the product with representative cases before broadening scope.

From a PM perspective, I want to learn which step creates the most friction and where trust breaks. From an engineering perspective, I want to measure retrieval quality, state transitions, and correction patterns. The roadmap should follow those findings rather than a predetermined list of AI features.
