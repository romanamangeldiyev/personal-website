01 — Why I built it

Why I built it

Creators and freelancers often earn money through several platforms at once. YouTube, Patreon, Gumroad, sponsorships, and other sources each show their own numbers, which makes even a basic question — “how much did I actually make this month?” — unnecessarily difficult.

Allincome started from the idea that creator income should feel like one financial system, not five disconnected dashboards.

I co-founded the product and owned the technical stack during the project. The larger product vision included unified income visibility, analysis, and recommendations rather than only aggregation.

02 — Product idea

One place for creator income

The early product direction centered on connecting multiple income sources and showing earnings across daily, weekly, and monthly views. The landing experience was built around explaining that value proposition and testing how the idea resonated with creators.

  • Unify creator and freelancer income sources.
  • Make time-based earnings easier to understand.
  • Provide a base for future analysis and AI-driven recommendations.
  • Design around creators rather than traditional business accounting workflows.

04 — Build process

How the product took shape

The project was built as a startup product, so the engineering loop was tied closely to positioning and user feedback. The sequence was less “finish the architecture, then show it” and more “make the value concrete, put it in front of people, and decide what deserves deeper engineering.”

creator pain point → product hypothesis → landing + interaction design → user conversations → refine positioning → decide what to build next

That process also exposed an important product lesson: technical completeness is not the same as product-market fit. The project was eventually closed, but it became one of the clearest examples for me of how engineering decisions and market learning have to move together.

05 — Publishing

Build and deployment path

The application uses the standard Next.js development and production workflow. Local development runs with the Next.js dev server, while production checks use the framework build command before deployment.

  • Develop locally with the Next.js dev server.
  • Run linting before release.
  • Create a production build to catch framework and type-related issues.
  • Deploy through a Node-compatible host; the repository is structured for the standard Vercel path used by Next.js projects.
06 — Why it matters

Why I still keep a failed product in my portfolio

Allincome did not become the company we intended to build. That is exactly why it belongs here. It taught me how much of product engineering happens outside the codebase: problem selection, sequencing, positioning, user conversations, and deciding when not to keep building.

The technical takeaway was end-to-end ownership. The product takeaway was that the right system built around the wrong assumption is still the wrong product.
